# Architecture Decision Records
**Автор:** Александр Кузив  
**Проект:** Secure Credit Hub

Этот документ содержит хронологический журнал ключевых архитектурных решений (ADR), принятых в процессе проектирования и реализации распределенной финтех-платформы **Secure Credit Hub**. Каждая запись фиксирует контекст, выбранное решение и технические компромиссы.

## ADR-001: Выбор микросервисной архитектуры с изолированными базами данных (Database-per-Service)

### Статус
Принято (Accepted)

### Контекст
Финтех-платформа Secure Credit Hub должна обеспечивать высокий уровень изоляции данных, независимое масштабирование различных бизнес-доменов (платежи, валюты, кредитные карты, пользователи) и минимизировать риски каскадных сбоев, когда падение одного модуля (например, аналитики) ломает проведение транзакций.

### Решение
Было принято решение отказаться от монолитной архитектуры в пользу **микросервисной архитектуры**. Каждый домен (`Users`, `Currencies`, `Payments`, `Credit Cards`) вынесен в отдельное Java-приложение (Spring Boot), упакован в Docker-контейнер и обладает полностью изолированной базой данных PostgreSQL (**паттерн Database-per-Service**). Межсервисное взаимодействие осуществляется строго через защищенные API-контракты шлюза.

### Последствия и компромиссы (Trade-offs)
* **Плюсы:** Полная изоляция сбоев на уровне БД, возможность независимого деплоя и горизонтального масштабирования (например, масштабирование только сервиса платежей в пиковые нагрузки).
* **Минусы:** Сложность поддержания консистентности данных (отсутствие ACID-транзакций между базами данных), необходимость внедрения распределенных транзакций (Сага) и усложнение локального развертывания.

## ADR-002: Внедрение реактивного неблокирующего стека (Spring WebFlux) для ядра платежей

### Статус
Принято (Accepted)

### Контекст
Платежный модуль (`Payments Microservice`) и шлюз API Gateway являются наиболее нагруженными компонентами системы. Традиционная модель "один поток на запрос" (Thread-per-Request) в классическом Spring MVC приводит к быстрому исчерпанию пула потоков веб-сервера (Tomcat) при длительном ожидании ответов от внешних систем (SEPA, Bizum), что снижает пропускную способность шлюза.

### Решение
Для реализации API Gateway и критических эндпоинтов `Payments Microservice` выбран реактивный фреймворк **Spring WebFlux** и неблокирующий HTTP-клиент **WebClient** (на базе веб-сервера Netty). Обработка платежных транзакций переведена на асинхронные, неблокирующие рельсы (`Mono`/`Flux`).

### Последствия и компромиссы (Trade-offs)
* **Плюсы:** Экстремально высокая пропускная способность при минимальном потреблении оперативной памяти и потоков процессора. Система не зависает при ожидании ответов от долгих внешних банковских API.
* **Минусы:** Повышение сложности написания и отладки кода. Необходимость строгого контроля отсутствия блокирующих вызовов в реактивных потоках. Временное использование блокирующего `.block()` в административных сценариях (таких как Сага обновления курсов) зафиксировано как технический долг (Technical Debt).

## ADR-003: Оркестрация распределенных транзакций с помощью паттерна Сага и резервированием в DLQ

### Статус
Принято (Accepted)

### Контекст
Поскольку базы данных сервиса Валют и сервиса Статистики/Мониторинга изолированы (ADR-001), операция обновления валютного курса администратором требует изменения данных в нескольких независимых узлах. Если сервис валют обновит курс, а сервис статистики упадет — система окажется в рассинхронизированном, неконсистентном состоянии.

### Решение
Реализован паттерн **Saga на основе оркестрации (Orchestration-based Saga)**, где API Gateway выступает координатором транзакции.
1. Шлюз синхронно запрашивает текущее состояние курса (делает бэкап).
2. Выполняет обновление в сервисе Валют.
3. Отправляет эвент в сервис Статистики.
   При сбое на любом этапе блок `catch` активирует компенсирующую транзакцию `rollbackSaga()`, которая возвращает старые цены назад. В случае сбоя самого отката (тотальный крах сети) инцидент пишется в локальный эндпоинт отказов интеграции (`/integration/failures`), выполняющий роль **Dead Letter Queue (DLQ)** для последующего аудита.

### Последствия и компромиссы (Trade-offs)
* **Плюсы:** Гарантия итоговой консистентности (Eventual Consistency) данных в распределенной системе без использования тяжелых и неэффективных двухфазных коммитов (2PC). Автоматический откат изменений при авариях.
* **Минусы:** Наличие временной связанности (Temporal Coupling) из-за синхронного ожидания по HTTP. В будущем планируется миграция Саги на асинхронный брокер сообщений (Apache Kafka).

## ADR-004: Использование паттернов Circuit Breaker и Retry для отказоустойчивости API

### Статус
Принято (Accepted)

### Контекст
В распределенной системе Secure Credit Hub шлюз постоянно обращается к удаленным сервисам (например, для чтения курсов валют). При падении контейнера валют или сетевом сбое запросы клиентов начнут копиться на шлюзе, таймауты забьют пул потоков, и шлюз упадет целиком (каскадный сбой).

### Решение
Эндпоинты чтения защищены аннотациями фреймворка **Resilience4j**: `@Retry` и `@CircuitBreaker`. При кратковременном сбое система автоматически делает повторные попытки (Retry). Если сервис стабильно отвечает ошибками, Circuit Breaker "размыкает цепь" и шлюз мгновенно направляет трафик в резервный метод (`Fallback`), минуя реальные сетевые запросы к упавшему сервису.

### Последствия и компромиссы (Trade-offs)
* **Плюсы:** Полная защита шлюза от лавинообразных падений зависимых сервисов. Клиенты гарантированно получают быстрый, понятный ответ об ошибке (`503 Service Unavailable`) или сохраненные в кэше данные вместо бесконечного ожидания.
* **Минусы:** Требуется тонкая ручная настройка параметров скользящего окна ошибок, таймаутов и количества попыток в `application.yml`, чтобы избежать ложных срабатываний предохранителя.

## ADR-005: Стандартизация сквозного трассирования с помощью Correlation ID

### Статус
Принято (Accepted)

### Контекст
При поиске багов в микросервисной архитектуре крайне сложно сопоставить логи шлюза, платежного сервиса и авторизации для одного конкретного пользовательского клика, так как они пишутся в разные файлы и контейнеры.

### Решение
Утвержден стандарт сквозного логирования: каждый входящий HTTP-запрос на шлюзе проверяется на наличие заголовка `X-Correlation-ID`. Если его нет, шлюз генерирует уникальный `UUID`. С помощью реактивных фильтров и заголовков `WebClient` этот ID пробрасывается через все внутренние HTTP-вызовы и сообщения. Каждый лог во всех контроллерах обязан начинаться строго с префикса `[Correlation-ID: {uuid}]`.

### Последствия и компромиссы (Trade-offs)
* **Плюсы:** Время локализации ошибок и разбора инцидентов в Kibana или Grafana Loki сокращается до нескольких секунд. Полная видимость сквозного пути транзакции.
* **Минусы:** Небольшие накладные расходы на ручную или полуавтоматическую передачу заголовка в коде и конфигурациях HTTP-клиентов.
