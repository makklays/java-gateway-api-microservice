# Technical Debt Log
**Автор:** Александр Кузив  
**Проект:** Secure Credit Hub

В данном документе зафиксирован технический долг распределенной системы **Secure Credit Hub**. Лог используется для отслеживания архитектурных компромиссов, временных решений и неоптимальных участков кода, которые требуют рефакторинга для обеспечения долгосрочной масштабируемости, производительности и надежности платформы.

---

## 🛑 1. Критический приоритет (High Priority) — Устранить в первую очередь

### TD-001: Использование блокирующих вызовов `.block()` на путях Саги
* **Компонент:** `API Gateway` / `CurrencyController`
* **Контекст:** В методе оркестрации распределенной транзакции `propagateCurrencyUpdate` и сопутствующих фейлбэках используется реактивный клиент `WebClient`, но вызовы завершаются синхронным методом `.block()`.
* **Бизнес-риск:** **Архитектурное бутылочное горлышко (Bottleneck).** Синхронное ожидание ответа от удаленного микросервиса валют блокирует рабочий поток веб-сервера шлюза. При высокой нагрузке или задержках на стороне микросервиса валют пул потоков шлюза быстро исчерпается, что парализует работу других (даже не связанных) эндпоинтов, включая модуль реактивных платежей.
* **Решение:** Полностью переписать цепочку Саги на реактивные операторы (`flatMap`, `zip`, `onErrorResume`) без использования `.block()`, возвращая из контроллера чистый `Mono<ResponseEntity<Map<String, Object>>>`.

### TD-002: Отсутствие Circuit Breaker на деструктивных операциях (PUT/POST)
* **Компонент:** `API Gateway` / `CurrencyController` (метод `updateCurrencyRate`)
* **Контекст:** Эндпоинты чтения курсов валют защищены предохранителем `@CircuitBreaker`, однако метод модификации курса напрямую вызывает удаленный микросервис без защиты.
* **Бизнес-риск:** Если микросервис валют полностью отключится, администраторы при попытке обновить курс будут сталкиваться с долгим зависанием шлюза по таймауту. Потоки будут заняты мертвыми ожиданиями, снижая общую отказоустойчивость шлюза.
* **Решение:** Покрыть метод `updateCurrencyRate` аннотацией `@CircuitBreaker` с выделенным профилем конфигурации и настроить мгновенный `Fallback`, возвращающий ошибку `503 Service Unavailable` без долгого сетевого ожидания.

## ⚡ 2. Средний приоритет (Medium Priority) — Плановый рефакторинг

### TD-003: Временная связанность микросервисов (Temporal Coupling) в Саге через HTTP
* **Компонент:** Взаимодействие `API Gateway` ➔ `Currencies Service` ➔ `Monitoring Service`
* **Контекст:** Распределенная транзакция обновления и репликации курсов валют координируется шлюзом последовательно через синхронные HTTP-запросы (REST API).
* **Бизнес-риск:** Низкая отказоустойчивость транзакции. Если в момент отправки лога статистики сеть моргнет, шлюзу приходится инициировать тяжелую процедуру отката курса назад через повторный HTTP PUT. Система сильно зависит от сиюминутной доступности всех участников цепочки по сети.
* **Решение:** Перевести архитектуру Саги с синхронной REST-оркестрации на **событийно-ориентированную (Event-Driven Architecture)**. Шлюз должен лишь атомарно обновить курс и опубликовать событие `CurrencyRateUpdatedEvent` в брокер сообщений (Apache Kafka). Сервис статистики и другие подписчики заберут эти данные асинхронно и гарантированно (благодаря механизму доставки Kafka At-Least-Once).

### TD-004: Ручная валидация входных параметров (Payload Maps) в контроллерах
* **Компонент:** `CurrencyController`, `PaymentController`
* **Контекст:** Извлечение параметров из тела запроса выполняется вручную из сырых структур данных: `incomingPrices.get("buy") != null ? Double.valueOf(...) : null`, с последующим ручным написанием `if-else` блоков для проверки на `null`.
* **Бизнес-риск:** Высокая вероятность упустить граничные случаи, засорение бизнес-логики контроллера бойлерплейт-кодом, усложнение поддержки и масштабирования контрактов API. Риск получения `NullPointerException` или `ClassCastException` в рантайме при передаче некорректных типов данных клиентом.
* **Решение:** Заменить сырые `Map<String, Object>` на строго типизированные Java Record-классы (**DTO**). Внедрить декларативную валидацию через спецификацию **Jakarta Validation** (аннотации `@NotNull`, `@Positive`, `@NotBlank`). Позволить Spring автоматически валидировать объекты с помощью аннотации `@Valid` на входе в метод.

## 🐢 3. Низкий приоритет (Low Priority) — Оптимизация производительности

### TD-005: Отсутствие кэширования на высоконагруженных эндпоинтах чтения
* **Компонент:** `API Gateway` ➔ эндпоинт `/api/v1/currencies/base-currencies`
* **Контекст:** Каждый раз, когда пользователь запрашивает список валют или баланс кредитной карты, система выполняет сквозной HTTP-запрос к нижележащему микросервису валют.
* **Бизнес-риск:** Избыточная сетевая нагрузка и падение производительности UI. Курсы валют Национального банка Украины не изменяются ежесекундно. Постоянные сетевые запросы за статичными данными неэффективно расходуют ресурсы процессора и полосу пропускания.
* **Решение:** Внедрить распределенное кэширование на базе **Redis** (или локальное кэширование Caffeine Cache на уровне шлюза) для эндпоинтов чтения курсов со временем жизни кэша (TTL) в 10–15 минут. При падении сервиса валют кэш также может выступать в роли "вечного" фейлбэка (Stale-While-Revalidate).
