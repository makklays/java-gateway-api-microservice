# Data Flow Diagrams (Диаграммы потоков данных)
**Автор:** Александр Кузив  
**Проект:** Secure Credit Hub

Этот документ описывает, как данные перемещаются между микросервисами в системе **Secure Credit Hub**. Он охватывает основные бизнес-сценарии: синхронное сквозное обновление курсов валют (Сага), реактивную обработку платежей, асинхронную репликацию данных через брокер сообщений Apache Kafka и сквозную трассировку транзакций.

---

## 📑 1. Общие принципы движения данных (Data Flow Principles)

Для обеспечения высокой отказоустойчивости, безопасности и консистентности данных в распределенной системе применяются следующие стандарты:
*   **Сквозная идентификация транзакций (Correlation ID):** Каждый входящий запрос на `API Gateway` маркируется уникальным заголовком `X-Correlation-ID`. Данный идентификатор передается по всей цепочке вызовов (как через REST HTTP, так и внутри метаданных сообщений Kafka), связывая распределенные логи в единый трейс.
*   **Изоляция баз данных:** Микросервисы общаются строго через API контракты (REST) или события (Kafka). Прямой доступ одного сервиса к базе данных другого категорически запрещен.
*   **Гибридный подход взаимодействия:**
    *   **Синхронный (REST HTTP):** Для мгновенных операций чтения (запрос курса валюты) и оркестрации критических транзакций.
    *   **Асинхронный (Event-Driven через Kafka):** Для репликации данных, логирования статистики, аудита и обработки тяжелых фоновых задач.

## 🔄 2. Диаграмма 1: Синхронная Сага обновления курса валют (REST Orchestration)

Сценарий описывает транзакционный процесс изменения цен покупки/продажи валюты администратором с автоматическим резервным копированием и механизмом компенсации (Rollback) в случае аварии.

```
[ Администратор ] 
       │ 
       │ 1. PUT /base-currencies/{code}/propagate (incomingPrices)
       ▼
┌────────────────────────────────────────────────────────────────────────┐
│                              API GATEWAY                               │
│  (Генерация X-Correlation-ID, Первичная валидация: buy < sell)         │
└──────┬──────────────────────────────────────────────────────────┬──────┘
       │                                                          │
       │ 2. GET /currencies/code/{code}                           │ 4. POST /integration/events
       │    (Запрос бэкапа старого курса)                         │    (Ивент: CURRENCY_RATE_UPDATED)
       ▼                                                          ▼
┌──────────────────────────────┐                          ┌──────────────┐
│      CURRENCIES SERVICE      │                          │ MONITORING & │
│                              │                          │  STATISTICS  │
└──────┬───────────────────────┘                          └──────────────┘
       │ 
       │ 3. PUT /currencies/code/{code} 
       │    (Запись нового курса в БД)
       ▼
   [ УСПЕХ ] ──► Возврат клиенту 200 OK
```

### Сценарий сбоя и компенсирующая транзакция (Rollback Flow):
Если **Шаг 4** (отправка статистики) падает или `Currencies Service` возвращает ошибку на этапе сохранения:
1. `API Gateway` перехватывает исключение в блоке `catch`.
2. Оркестратор отправляет компенсирующий запрос `PUT` в `Currencies Service`, передавая сохраненные на Шаге 2 данные (`previousRate`).
3. Направляется аварийный ивент `CURRENCY_RATE_ROLLBACK` в сервис статистики.
4. В случае тотального краха сети, шлюз фиксирует инцидент локально или через эндпоинт `/integration/failures` (Dead Letter Queue).

## 💳 3. Диаграмма 2: Реактивная инициализация платежа (High-Load Reactive Flow)

Сценарий демонстрирует неблокирующий нереактивный ввод-вывод (`Spring WebFlux`) при инициализации транзакций по кредитным картам.

```
[ Клиент (Мобильное приложение / UI) ]
       │
       │ 1. POST /api/v1/payments (Payload, Auth Token)
       ▼
┌────────────────────────────────────────────────────────────────────────┐
│                              API GATEWAY                               │
│  (Проверка JWT-токена, Валидация ролей, Извлечение X-Correlation-ID)    │
└──────┬─────────────────────────────────────────────────────────────────┘
       │
       │ 2. Неблокирующий вызов (Mono<Map>) via WebClient
       ▼
┌────────────────────────────────────────────────────────────────────────┐
│                            PAYMENTS SERVICE                            │
│  (Асинхронный прием запроса, перевод транзакции в статус PENDING)       │
└──────┬─────────────────────────────────────────────────────────────────┘
       │
       │ 3. Мгновенный реактивный ответ (Status: PENDING) без блокировки потока
       ▼
[ Клиент получает быстрый ответ 202 Accepted ]
```

## 🛡️ 5. Безопасность и валидация данных на путях потоков (Data Security)

В процессе перемещения данных между узлами Secure Credit Hub применяются следующие механизмы защиты:
1.  **Периметр безопасности (Edge Validation):** `API Gateway` проверяет подпись входящего `JWT Bearer` токена. Если токен просрочен или скомпрометирован, поток данных прерывается на входе, возвращая `401 Unauthorized`.
2.  **Шифрование при передаче (Data-in-Transit):** Все межсервисные REST-коммуникации внутри сети Docker контейнеров используют протокол HTTPS. Взаимодействие с Apache Kafka защищено механизмами SASL/SSL.
3.  **Валидация бизнес-правил:** Проверка полей на уровне Dto (например, проверка коммерческого спреда `sellPrice > buyPrice`) происходит до момента отправки данных во внутренние системы хранения, гарантируя защиту баз данных от некорректных состояний.
