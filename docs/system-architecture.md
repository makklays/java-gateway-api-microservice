# System Architecture Document
**Автор:** Александр Кузив  
**Проект:** Secure Credit Hub

## Введение
Система **Secure Credit Hub** разработана как отказоустойчивая, безопасная и высокомасштабируемая финтех-платформа для управления кредитными картами, мультивалютной конвертации и проведения платежей. Главная цель создания системы — предоставить надежную цифровую среду для финансовых операций, минимизируя время простоя и исключая потерю данных при распределенных транзакциях.

**Целевая аудитория:** Клиенты банка (держатели мультивалютных кредитных карт), операционные менеджеры и администраторы финансовой платформы.

**Задачи, которые решает система:**
*   **API Gateway & Маршрутизация:** Единая точка входа для клиентских приложений, обеспечивающая сквозную безопасность и оркестрацию транзакций.
*   **Управление кредитными продуктами:** Полный жизненный цикл кредитных карт, валидация, ведение баланса, расчет лимитов и бонусных баллов лояльности.
*   **Мультивалютная конвертация:** Интеграция с данными курсов валют Национального банка Украины (НБУ) для проведения точных кросс-национальных расчетов.
*   **Проведение платежей:** Поддержка различных типов транзакций, включая SEPA, Bizum и внутренние переводы между счетами.
*   **Изоляция сбоев:** Защита системы от каскадных падений при отказе отдельных компонентов.

## Архитектурный стиль
Система спроектирована на основе **микросервисного архитектурного подхода**, где каждый сервис инкапсулирует строго определенную бизнес-функцию в рамках своей доменной области (Domain-Driven Design / Bounded Context).

**Ключевые принципы реализации стиля:**
*   **Разделение ответственности (Separation of Concerns):** Каждый микросервис (Users, Currencies, Credit Cards, Payments, Monitoring) автономен, имеет собственную кодовую базу и изолированный слой хранения данных (Database-per-Service на базе PostgreSQL). Это исключает жесткую связность на уровне таблиц БД.
*   **Независимость развертывания:** Все микросервисы упакованы в независимые Docker-контейнеры. Модификация, обновление или масштабирование одного сервиса (например, сервиса платежей) никак не затрагивает работоспособность других компонентов системы.
*   **Оркестрация транзакций (Saga Pattern):** Для поддержания консистентности данных между изолированными сервисами используется синхронная Сага с механизмом компенсирующих транзакций (`rollbackSaga`) и логированием критических сбоев в Dead Letter Queue (DLQ).

## Технологический стек
Выбранный стек технологий ориентирован на построение отказоустойчивых корпоративных приложений с высоким уровнем реактивности и безопасности:

*   **Язык программирования:** Java 17+ (использование современных конструкций, record-классов, эффективных практик чистого кода SOLID).
*   **Фреймворки:** Spring Boot (основа для создания изолированных микросервисов), Spring WebFlux (реактивный неблокирующий стек для высоконагруженных пайплайнов, таких как инициация платежей).
*   **Безопасность:** Spring Security, OAuth2 Authorization Server, OpenID Connect для централизованной выдачи токенов.
*   **Базы данных и миграции:** PostgreSQL (изолированные реляционные хранилища для каждого сервиса), Hibernate/JPA (для синхронных слоев данных), Flyway (инструмент контроля версий и автоматической миграции схем БД).
*   **Интеграционная шина проекта:** **Apache Kafka** — используется в качестве отказоустойчивого брокера сообщений. Обеспечивает быструю, надежную и асинхронную передачу данных между сервисами, гарантируя доставку событий и развязывая компоненты системы во времени (устранение Temporal Coupling).
*   **Контейнеризация и оркестрация:** Docker (изоляция окружения), Docker Compose (локальный запуск и линковка всей инфраструктуры), с заделом на миграцию в Kubernetes (K8s).
*   **Тестирование:** JUnit 5, Mockito, Testcontainers (интеграционное тестирование в реальных Docker-контейнерах баз данных и WireMock).

## Протоколы взаимодействия сервисов
Взаимодействие между компонентами системы Secure Credit Hub стандартизировано и разделено по типам нагрузок:

*   **REST API и HTTP-методы:** Использование синхронного и реактивного REST (`WebClient`) для внешних запросов клиентов и синхронных цепочек Саги. Применение строгих стандартов HTTP-методов (`GET` — чтение, `POST` — создание, `PUT` — обновление/компенсация) и универсального формата данных JSON обеспечивает единый стандарт общения между сервисами и значительно упрощает их интеграцию.
*   **Асинхронные события (Event-Driven):** Использование протокола передачи сообщений Apache Kafka для обмена бизнес-событиями (например, фиксация аудита, отправка уведомлений, обработка статистики), что снижает задержки (latency) основного потока выполнения.
*   **Сквозные заголовки:** Каждый запрос включает обязательный заголовок `X-Correlation-ID` для сохранения контекста вызова при переходе границ микросервисов.

## Масштабируемость
Архитектура Secure Credit Hub изначально закладывает возможности для линейного роста нагрузок:

*   **Стратегии горизонтального масштабирования:** Поскольку микросервисы спроектированы как приложения без сохранения состояния (**Stateless**), любой из них (например, API Gateway или Payments Service) может быть мгновенно размножен на несколько экземпляров (Scale-out) в Docker-окружении или Kubernetes.
*   **Балансировка нагрузки:** Внешний трафик распределяется между запущенными экземплярами микросервисов, распределяя вычислительную нагрузку и исключая появление единой точки отказа (Single Point of Failure).
*   **Обеспечение высокой доступности при пиковых нагрузках:** Реактивный стек Spring WebFlux позволяет обрабатывать тысячи одновременных соединений минимальным пулом потоков за счет неблокирующего ввода-вывода (Event Loop). В синхронных слоях для защиты ресурсов баз данных применяются пулы соединений (HikariCP).

### Расчет целевой производительности системы (Capacity Planning)
Для подтверждения жизнеспособности архитектуры шлюза и платежных модулей произведен расчет ожидаемой нагрузки на основе бизнес-метрик:
* **Активная аудитория (DAU):** 40 000 000 пользователей в день.
* **Пользовательская активность:** 5–10 действий (кликов/запросов) на одного пользователя в сутки (среднее значение — 7.5 кликов).

#### Математический расчет:
* **Общий объем трафика за сутки:**
  ```text
  40 000 000 пользователей × 7.5 запросов = 300 000 000 запросов в день
  ```

* **Средняя нагрузка в секунду (Average RPS):**
  ```text
  300 000 000 запросов / 86 400 секунд ≈ 3 472 запроса в секунду
  ```

* **Пиковая нагрузка в секунду (Peak RPS):**
  Финтех-системы характеризуются высокой неравномерностью трафика в течение суток (бизнес-часы, вечерние покупки). С применением стандартного коэффициента неравномерности **K_peak = 2.5**, расчетная пиковая мощность составляет:
  ```text
  3 472 RPS × 2.5 ≈ 8 680 RPS
  ```

#### Стратегия горизонтального масштабирования под пиковую нагрузку:
* **Архитектурный ответ на 8680 RPS:** Классическая синхронная архитектура (Thread-per-Request) потребовала бы огромного пула потоков процессора и сотен серверов. Выбранный реактивный стек **Spring WebFlux (на базе Netty)** обрабатывает такой объем трафика асинхронно, задействуя фиксированное число потоков (равное числу ядер CPU), что минимизирует расходы на переключение контекста.
* **Балансировка нагрузки (Load Balancing):** На внешнем контуре перед API Gateway развертывается балансировщик (например, Nginx или HAProxy), который равномерно распределяет входящие 8680 RPS между несколькими инстансами (подами) шлюза.
* **Амортизация пиков через Apache Kafka:** Всплески транзакционной активности в `Payments Service` не передаются напрямую в сопутствующие сервисы (например, начисления баллов в `Credit Cards Service`). Платежи публикуются в Kafka, которая выступает буфером, позволяя зависимым сервисам выгребать сообщения в стабильном, комфортном для них темпе, полностью исключая падение системы из-за перегрузки.

## Мониторинг
Для обеспечения полной прозрачности работы распределенной системы внедрен развитый слой наблюдаемости (**Observability**):

*   **Сбор метрик:** Каждый микросервис содержит компонент **Spring Boot Actuator**, собирающий системные метрики (потребление памяти, CPU, состояние пула потоков) и предоставляющий эндпоинты хелсчеков (`/actuator/health`).
*   **Централизованное логирование:** Все логи стандартизированы под единый формат и содержат маркеры сервиса и временные метки. Системные сбои Саги и критические падения отката пишутся в изолированные таблицы/эндпоинты инцидентов (`/integration/failures`).
*   **Распределенная трассировка (Distributed Tracing):** Реализована на базе сквозного идентификатора **Correlation ID**. Уникальный UUID генерируется на уровне API Gateway при входе запроса в систему и принудительно пробрасывается во все последующие HTTP-вызовы и сообщения Kafka. Это позволяет мгновенно восстановить полную цепочку выполнения запроса по логам всех контейнеров.

## Безопасность системы
Защита конфиденциальных финансовых данных и API реализована на нескольких эшелонах:

*   **Аутентификация и авторизация:** Построены на базе протоколов **OAuth2** и **OpenID Connect**. Сервис `Users` выступает централизованным сервером авторизации, генерирующим криптографически подписанные, краткосрочные **Stateless JWT** токены. Доступ к конечным эндпоинтам разграничен на основе ролей (`@PreAuthorize("hasRole('USER'/'ADMIN')")`).
*   **Шифрование данных:** Весь сетевой трафик между клиентом, шлюзом и внутренними микросервисами защищен сквозным шифрованием (HTTPS/TLS). Чувствительные данные в базах данных (например, пароли) хэшируются с использованием стойких алгоритмов (BCrypt).
*   **Меры предосторожности и защита API:**
    *   **Валидация входящих данных:** Реализована строгая бизнес-валидация на уровне API Gateway (например, проверка корректности спреда валют `sellPrice > buyPrice`) и валидация типов данных, отсекающая некорректные запросы до их передачи во внутренний контур.
    *   **Rate Limiting (Ограничение частоты запросов):** Механизм, защищающий эндпоинты шлюза (особенно платежные) от DoS/DDoS атак и brute-force подбора, лимитируя количество запросов с одного IP-адреса или токена в единицу времени.
    *   **Паттерн Circuit Breaker (Resilience4j):** Защищает внутренний периметр от лавинообразных падений. Если один из сервисов начинает сбоить, Circuit Breaker размыкает цепь, изолируя дефектный узел и возвращая безопасный заглушечный ответ (`Fallback`), сохраняя общую доступность системы.
